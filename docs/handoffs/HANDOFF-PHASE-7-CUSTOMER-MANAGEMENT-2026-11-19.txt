============================================================
5. CUSTOMER IDENTITY LOGIC
============================================================

- Decouples immutable `customerId` from `phoneNormalized`.
- Lightweight name normalization (`NFKC`, trim, collapse spaces, lowercase + compact
  space-variant equivalence for `Arief Music` / `Ariefmusic` / `ARIEF MUSIC`).
- Five explicit resolution states (`resolveCustomerIdentityCandidates`):
  `NO_MATCH`, `HISTORICAL_ONLY` (recycled number), `EXACT_MATCH`, `SINGLE_CONFLICT`,
  and `MULTIPLE_MATCHES`.
- Archived and merged profiles are never silently selected for new bookings; merged
  references resolve safely to their canonical active target.

============================================================
6. PHONE NORMALIZATION
============================================================

Shared utility `src/features/admin/customer/utils/phone-number.js`:
- Normalizes `081234567890`, `+6281234567890`, `6281234567890`, `+62 812-3456-7890`,
  `(0812) 3456 7890`, and `006281234567890` identically to `+6281234567890`.
- Preserves non-Indonesian international numbers with explicit `+` / `00` country codes.
- Rejects empty, alphabetic, or out-of-range numbers.
- Deterministic SHA-256 hashing (`getPhoneNumberHash` via Web Crypto + identical pure-JS
  FIPS 180-4 `getPhoneNumberHashSync`).

============================================================
7. DUPLICATE & IDENTITY SCENARIOS COVERED
============================================================

1. Same phone + same name / alias / whitespace variant -> auto reuse (`CUSTOMER EXISTING`).
2. Same phone + different name -> `CustomerIdentityConflictDialog` (`Gabungkan ke <Name>`,
   `Buat Profil Terpisah`, `Periksa Kembali`).
3. Same phone + multiple active profiles -> candidate card selector (never auto-picks by
   highest booking count).
4. Same name + different phone -> distinct profiles with `Nama mirip, nomor berbeda` badge.
5. Shared family/band/office number -> `SHARED NUMBER` group card with separate histories
   and explicit `Merge History` action.
6. Customer changes phone -> atomic update storing old phone in `previousPhones`, searchable
   historically, conflict check if new phone occupied, historical booking `phone` untouched.
7. Recycled phone number -> detected via `historicalCustomerIds` (`HISTORICAL_ONLY`), creates
   fresh separate profile without auto-linking to previous owner.
8. One customer, multiple band names -> single profile; `Band / Project History` lists all
   distinct band snapshots.
9. Invalid/missing legacy phone -> routed to `Needs Review` for explicit phone fix or linking.
10. Cancelled / No-Show bookings -> profile retained, `bookingCount` not decremented,
    visible in history.
11. Edit/reschedule booking -> retains `customerId`; editing booking phone updates contact
    snapshot only.

============================================================
8. MERGE IMPLEMENTATION
============================================================

- Virtual history merge via `mergeCustomerProfiles()` inside a single atomic Firestore
  transaction (`CustomerMergeDialog` preview with target/source selector & swap button).
- Combines `historyCustomerIds`, `nameAliases`, `previousPhones`, `bookingCount`,
  `firstBookingDate`, and `lastBookingDate` onto the active target profile.
- Sets source `status = 'merged'` and `mergedIntoCustomerId = targetId`, updates
  `customerPhoneIndex`, and leaves every historical booking document completely untouched.
- `useCustomerBookingHistory()` queries `historyCustomerIds` in `<= 10`-ID Firestore `in`
  chunks, deduplicates by `booking.id`, sorts descending, and paginates with `Load More`.

============================================================
9. BOOKING TRANSACTION INTEGRATION
============================================================

- `createBooking()` runs all reads before all writes inside ONE atomic Firestore transaction:
  `customers/{customerId}`, `customerPhoneIndex/{phoneHash}`, `bookings/{bookingId}`,
  30-min `bookingSlots`, and `bookingEvents/{eventId}`.
- Slot conflicts abort before any writes -> zero orphan customer profiles.
- Pre-generated stable `bookingId`, `eventId`, and `customerId` guarantee full idempotency
  on retry (bookingCount never increments twice, aliases never duplicate).
- Validates `expectedPhoneIndexVersion` to reject stale concurrent identity conflicts.

============================================================
10. LEGACY IMPORT RESULTS
============================================================

- `scanLegacyBookingsPreview()` scans unlinked bookings via bounded pagination with zero
  writes on render, grouping strictly by `(phoneNormalized + normalizedName)` and placing
  invalid/missing phone records into `Needs Review`.
- `importLegacyBookingHistory()` executes resumable batches (`<= 400` writes/batch) using
  deterministic legacy Customer IDs (`cust_leg_<hash>`), updating ONLY `customerId`,
  `phoneNormalized`, `updatedAt`, `updatedByUid`, `version` on legacy bookings without
  touching financial snapshots, slots, or events.
- `resolveNeedsReviewLegacyBooking()` links invalid legacy bookings via corrected phone
  or selected active profile.
