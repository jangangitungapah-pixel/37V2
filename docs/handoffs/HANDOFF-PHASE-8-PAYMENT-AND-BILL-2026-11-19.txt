4. FIRESTORE COLLECTIONS
============================================================

1. `invoices/{invoiceId}` (`inv_{bookingId}`, 20 fields):
   - Identity: `invoiceNumber`, `bookingId`, `customerId`, `invoiceStatus`, `currency` (`IDR`).
   - Immutable snapshots: `customerSnapshot`, `bookingSnapshot`, `financialSnapshot` (zero internal commissions).
   - Transactional aggregates: `amountPaid`, `balanceDue`, `paymentStatus`, `lastPaymentTransactionId`.
   - Metadata/Audit: `invoiceDate`, `dueDate`, `voidReason`, `createdAt`, `createdByUid`, `updatedAt`, `updatedByUid`, `version`.
2. `paymentTransactions/{transactionId}` (15 fields, append-only):
   - References: `invoiceId`, `invoiceNumber`, `bookingId`, `customerId`.
   - Entry: `transactionType` (`payment` | `reversal`), `amount` (int Rupiah > 0), `currency`, `paymentMethod` (`cash` | `transfer` | `qris` | `other`), `receivedAt`, `referenceNumber`, `notes`.
   - Provenance: `source` (`booking_initial_payment` | `manual` | `legacy_initial_snapshot` | `reversal`), `reversalOfTransactionId`, `recordedByUid`, `createdAt`.

============================================================
5. INVOICE NUMBER FORMAT
============================================================

- Pattern: `37MS-YYYYMMDD-XXXXXXXXXXXX`
- Deterministic from `bookingDate` (`YYYYMMDD`) + 12 uppercase hex chars of
  `SHA-256("37ms:invoice:" + bookingId)`.
- Stable across retries without mutable counter documents; locked immutable in Firestore Rules.

============================================================
6. AUTOMATIC INVOICE GENERATION FLOW
============================================================

- Executed atomically inside `createBooking()` (`calendar-booking-service.js`) with all reads
  preceding all writes:
  Customer + PhoneIndex + Booking + BookingSlots + BookingEvent + `invoices/inv_{bookingId}`
  + optional `paymentTransactions/pay_initial_{bookingId}`.
- Slot conflicts or validation errors abort before any writes -> zero orphan invoices or payments.
- Retries with the same `bookingId` + `eventId` return the committed booking idempotently.

============================================================
7. PAYMENT TRANSACTION FLOW
============================================================

- `recordInvoicePayment()` uses a pre-generated stable `transactionId` inside `runTransaction`:
  reads invoice + transaction ID first, verifies `issued` status, `expectedVersion`, positive
  integer Rupiah amount, and `amount <= balanceDue` (overpayment protection), then writes the
  append-only transaction and updates `amountPaid`, `balanceDue`, `paymentStatus`,
  `lastPaymentTransactionId`, and `version + 1` atomically.
- Concurrent payment attempts serialize via optimistic concurrency (`version` / `balanceDue`)
  preventing negative balances.
- `reversePaymentTransaction()` creates deterministic append-only reversal records
  (`pay_rev_{originalTxId}`) with mandatory reason and explicit non-refund confirmation UX.
- `voidInvoice()` requires `amountPaid === 0` and mandatory reason; void invoices reject new payments.

============================================================
8. INITIAL PAYMENT INTEGRATION
============================================================

- Booking Form initial statuses (`unpaid` / `partial` / `paid`) remain preserved on `bookings`
  as immutable initial snapshots (`initialPaymentStatus`, `initialPaidAmount`, `paymentMethod`).
- When `initialPaidAmount > 0`, `createBooking()` atomically writes `pay_initial_{bookingId}`
  with `source = 'booking_initial_payment'`.
- When `initialPaidAmount === 0`, no payment transaction is written (`amountPaid = 0`, `unpaid`).

============================================================
9. LEGACY INVOICE RECONCILIATION
============================================================

- `scanLegacyBookingsForInvoicesPreview()` scans historical bookings via bounded pagination
  with zero writes on render, classifying inconsistent initial payments and cancelled/no-show
  records into `Needs Review`.
- `importLegacyBookingInvoices()` creates deterministic invoices (`inv_{bookingId}`) and
  `legacy_initial_snapshot` transactions (`pay_initial_{bookingId}`) in resumable batches
  (`<= 400` writes, keeping invoice/payment pairs atomic in the same batch), without touching
  historical bookings, slots, events, or customers, and with strict anti-double-counting on retry.
- `reconcileNeedsReviewLegacyBooking()` reconciles flagged items explicitly per record.
