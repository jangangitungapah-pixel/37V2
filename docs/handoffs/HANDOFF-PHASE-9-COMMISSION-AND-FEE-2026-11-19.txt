4. ELIGIBILITY & COMPLETION DATE LOGIC
============================================================

- Filters strictly by `bookings.actualCompletedAt` using `date-fns` and `@date-fns/tz`
  anchored in `Asia/Jakarta` (`This Month` default, `Last Month`, `Custom Date Range`).
- A booking is eligible iff:
  1. `sessionStatus === 'completed'`
  2. Valid `actualCompletedAt` timestamp within the active Jakarta period bounds
  3. `deliveryMode === 'studio'` and service is `rehearsal` or `recording`
  4. Valid V1 or V2 `commissionSnapshot`
  5. No existing `commissionPostingItems/{bookingId}`
  6. Payable total (`staff + recordingOperator`) > 0
- Strictly excludes `upcoming`, `in_progress`, `cancelled`, `no_show`, WFA services,
  bookings without valid `actualCompletedAt`, zero-payable records (including
  Owner-allocation-only records), and already-posted bookings.
- Bounded period pagination (`limit(pageSize + 1)`) surfaces `More sessions available` and
  `Load More Sessions` when more completed sessions exist so partial totals are never
  presented as complete period totals.

5. SNAPSHOT NORMALIZATION
============================================================

- Implemented in `src/features/admin/commission/utils/commission-snapshot.js`:
  - Supports V2 (`schemaVersion: 2`, per-role `staff` / `owner` / `recordingOperator` with
    basis `none | fixed | hourly | manual`, rate, integer Rupiah amount, `settingsVersion`)
  - Supports Legacy V1 compatibility (`staffBasis`, `staffRate`, `staffAmount`,
    `recordingOperatorAmount`, `settingsVersion`; treats `owner` allocation as `0`)
  - Preserves raw Firestore `commissionSnapshot` (`rawCommissionSnapshot`) without clamping
    malformed/negative data so missing, corrupted, or negative snapshots route reliably
    into `Needs Review` with zero silent recalculation from live Settings.

============================================================
6. FEE CATEGORY CALCULATION & RECIPIENT BOUNDARY
============================================================

- Payable categories:
  - `Staff Commission` (`Staff / Studio Guard`) = `commissionSnapshot.staff.amount`
  - `Recording Operator Fee` (`Recording Operator / External PIC`) = `commissionSnapshot.recordingOperator.amount`
  - `Total To Pay = Staff Commission + Recording Operator Fee`
- Reference-only category:
  - `Owner Allocation` = `commissionSnapshot.owner.amount`, stored for informational
    transparency only and strictly excluded from `Total To Pay` and `bookkeepingEntries`.
- Individual recipient names are not fabricated (`createdByUid` is never treated as fee earner).

7. FIRESTORE COLLECTIONS
============================================================

1. `commissionBatches/{batchId}` (15 fields, immutable):
   - Period (`periodStart`, `periodEnd`, `completionTimeZone: 'Asia/Jakarta'`), `bookingCount` (`1..100`),
     `staffCommissionTotal`, `recordingOperatorFeeTotal`, `payableTotal`,
     `ownerAllocationReferenceTotal`, `currency: 'IDR'`, `status: 'posted'`,
     `bookkeepingEntryIds`, `postedAt`, `postedByUid`, `createdAt`, `createdByUid`.
2. `commissionPostingItems/{bookingId}` (15 fields, deterministic doc ID === `bookingId`, immutable):
   - Links `batchId`, `bookingId`, `customerSnapshot`, `completedAt`, `serviceSnapshot`,
     exact historical `commissionSnapshot`, integer `staffPayableAmount`,
     `recordingOperatorPayableAmount`, `ownerAllocationReference`, `payableTotal`, `currency`,
     `status: 'posted'`, `postedAt`, `postedByUid`, `createdAt`.
3. `bookkeepingEntries/{entryId}` (13 fields, expense accrual contract):
   - Deterministic IDs: `bk_commission_{batchId}_staff` and `bk_commission_{batchId}_operator`
     (created strictly when each category > 0).
   - `sourceModule: 'commission-and-fee'`, `sourceType: 'commission_batch'`, `sourceId: batchId`,
     `entryType: 'expense_accrual'`, `category` (`'staff_commission' | 'recording_operator_fee'`),
     `description`, `amount`, `currency: 'IDR'`, `settlementStatus: 'unpaid'`, `occurredAt`,
     `postedAt`, `createdAt`, `createdByUid`.
4. `commissionReviewResolutions/{bookingId}` (9 fields, deterministic doc ID === `bookingId`, immutable):
   - Records explicit Owner acknowledgement (`status: 'dismissed_no_commission'`, `reason`,
     `snapshotIssue`, `customerSnapshot`, `completedAt`, `resolvedAt`, `resolvedByUid`, `createdAt`)
     so legacy/invalid Needs Review bookings can be marked resolved and hidden from the collapsible
     Needs Review banner without mutating historical `bookings` or creating fake `bookkeepingEntries`.

8. POSTING TRANSACTION FLOW & BOOKKEEPING INTEGRATION
============================================================

- `postCommissionBatch()` (`src/features/admin/commission/services/commission-posting-service.js`)
  executes inside `runTransaction` with all reads (`commissionBatches`, `bookkeepingEntries`,
  `bookings`, `commissionPostingItems`) before any writes:
  - Pre-generates stable `batchId` in `Confirm Commission Posting` so retries replay idempotently.
  - Enforces max `100` bookings per batch, active Owner role, `completed` status, optimistic
    `booking.version` & snapshot signature match, and absence of prior posting items.
  - Concurrent double-post attempts abort cleanly (`commission/already-posted`) with zero
    partial writes or duplicate `bookkeepingEntries`.
  - Posting creates `expense_accrual` entries (`settlementStatus: 'unpaid'`) and never alters
    `bookings.commissionSnapshot`, `customers`, `invoices`, or `paymentTransactions`.

9. FIRESTORE RULES & OWNER AUTHORIZATION
============================================================

- Updated `firestore.rules` with `match /commissionBatches/{batchId}`,
  `match /commissionPostingItems/{itemId}`, `match /commissionReviewResolutions/{resolutionId}`,
  and `match /bookkeepingEntries/{entryId}`:
  - Active Owner only (`isActiveOwner()`) for `read` and `create`; `update` & `delete` denied.
  - Enforces `bookingId == itemId`, source booking `completed` (`studio` Rehearsal/Recording),
    `completedAt == booking.actualCompletedAt`, `commissionSnapshot == booking.commissionSnapshot`,
    V1/V2 amount consistency, `payableTotal == staff + operator` (Owner excluded), and atomic
    `existsAfter()` / `getAfter()` linkage to deterministic `bookkeepingEntries`.
  - `commissionReviewResolutions` verifies source booking is `completed` with matching
    `actualCompletedAt`, mandatory reason `3..300` chars, Owner UID, and strict immutability.
- Active Staff on `/admin/commission-and-fee` see `Owner Access Required` /
  `Read Only — Owner Approval Required` with zero privileged Firestore queries subscribed.
